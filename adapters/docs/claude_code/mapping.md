# Claude Code → ACS hook mapping

Each Claude Code hook event maps to an ACS `steps/*` method. The adapter (`src/acs/integrations/claude_code/adapter.py`) does the translation in both directions: Claude Code hook event → ACS JSON-RPC request, ACS decision → Claude Code response.

## Hook event mapping

| Claude Code hook | ACS step method | Notes |
|---|---|---|
| `SessionStart` | `steps/sessionStart` | Session bounds, sent once per session by the hook process that opens the session and built from its event (see Concurrency). A `SessionStart` with `source: resume` or `compact` in a session that already started sends nothing. After a `SessionEnd`, the next hook of the same Claude Code session (`--resume` and `--continue` reuse its `session_id`) opens a new ACS session, with its own `session_id`, handshake and `sessionStart`, whose `platform_context.host_session_id` names the Claude Code session; nothing is sent into the ended one. A Guardian `deny`, or a refusal of the request, refuses the session: every later step of it is denied in its hook's own shape. A `sessionStart` that gets no decision is recorded, and each later hook settles its step with its own fail posture; `sessionEnd`, which is audit-only, goes out under either posture and reports that failure (§6.4). Session-level — carries no `turn_id`. |
| `SessionEnd` | `steps/sessionEnd` | Session close (chain seal). Carries `summary.decision_failures`, the session's decision failures per failure class (§6.4). The adapter then marks the ACS session ended and removes its records. Session-level — no `turn_id`. |
| `UserPromptSubmit` | `steps/turnStart` **then** `steps/userMessage` | A prompt OPENS a turn: the adapter first emits a decision-eligible `steps/turnStart` (`triggered_by: user_message`; a Guardian MAY `deny` to block the whole turn), then the `steps/userMessage` carrying the `prompt`. Both — and every in-turn step below — carry `metadata.turn_id`. The `turn_id` is held in per-session state until the matching `Stop`. |
| `Stop` | `steps/agentResponse` **then** `steps/turnEnd` | End of a **turn** (every reply), not the session. When `last_assistant_message` carries the reply, the adapter first sends it as `steps/agentResponse` under the open turn. The reply has already reached the user, so a Guardian decision on it is recorded (`unenforceable_decision`) and the turn still ends. `steps/sessionEnd` "seals the chain" once per session, so mapping `Stop` there sealed it after every reply; `steps/turnEnd` (audit-only, `outcome: completed`) is the correct per-turn boundary and echoes the open turn's `turn_id`. A `Stop` with no open turn is skipped + audited (`turn_end_no_open_turn`) rather than emitting a fabricated `turn_id`. Claude Code runs no `Stop` after a user interrupt, so a turn still open when the next `UserPromptSubmit` arrives is closed first with a `steps/turnEnd` of outcome `interrupted`. |
| `StopFailure` | `steps/turnEnd` | The turn ended on an API error: `outcome: error`. Its `last_assistant_message` is the error text, so no `steps/agentResponse` is sent. Claude Code ignores this hook's output. |
| `PreToolUse` | `steps/toolCallRequest` | Fires before the tool runs. Decision gates execution. Carries `metadata.turn_id`. |
| `PreToolUse` with `tool_name="Agent"` (legacy: `"Task"`) | `steps/subagentStart` | The `Agent` tool IS Claude Code's subagent spawn (per the hooks reference; older builds named it `Task`, still matched), so it routes to the confused-deputy gate (ACS-Core requires `subagentStart` of a subagent-capable client) instead of the generic tool hook. All four required fields are real: `parent_step_id` is this step's own deterministic request_id (the delegation step and the spawn event are the same wire step on this platform), `subagent_session_id` is a uuid5 of the `tool_use_id` under a distinct namespace, `intent_derivation` is `derived_from_parent` (the Agent prompt is parent-authored — never `"fresh"`). The Guardian's decision translates back through the normal PreToolUse `permissionDecision` shape. `PostToolUse` for the Agent call stays `steps/toolCallResult` (it is honestly the tool's result); the separate `SubagentStop` event is not forwarded (see its row below). |
| `PostToolUse` | `steps/toolCallResult` | Fires after the tool runs. `tool_response` carries the output. A decision that keeps the output from Claude replaces it with `updatedToolOutput`, which "works for all tools": in the documented `stdout` / `stderr` / `interrupted` / `isImage` shape for `Bash`, as text for an MCP tool, and for another built-in tool such as `Read`, `Grep` or `WebFetch` in the shape of its own `tool_response`, each content string replaced by the withheld notice and each list emptied, since Claude Code ignores a replacement that does not match the tool's output schema. A result with no `tool_response` is blocked, which shows Claude the reason next to the original output, and recorded as `unenforceable_decision`. |
| `PostToolUseFailure` | `steps/toolCallResult` | Fires when a tool that started fails, including a Bash command that exits nonzero and an MCP tool's error result. `exit_status: failure`, the `error` text as the output, and `request_id_ref` from `tool_use_id`. The hook accepts only `additionalContext`, and Claude has already received the error, so a Guardian decision other than `allow` is given to Claude as context and recorded as `unenforceable_decision`; withholding output covers successful calls only. |
| `SubagentStop` | — not forwarded | `KNOWN_UNMAPPED`. `steps/subagentStop` is SHOULD-emit, and its `final_chain_hash` is optional for a framework with no session chain (since PR #21), but it requires the `subagent_session_id` its `subagentStart` sent, which the adapter derives from the Agent call's `tool_use_id`. `SubagentStop` carries the subagent's `agent_id` instead, and it also fires for Claude Code's internal agents, so the adapter cannot name the subagent session a stop ends. Mapping it needs the Agent call's `agent_id` recorded against its `tool_use_id`. |
| `Notification` | — not forwarded | `KNOWN_UNMAPPED`: it fires on permission and idle prompts, not on the model's reply, so it carries no `agentResponse` content. The reply goes out from `Stop`. `acs-claude-code-wire` no longer wires it, and wiring or unwiring removes the ACS hook an earlier version wired there. |

**Deliberately not mapped — `PreCompact`.** `steps/preCompact` requires `entries_to_compact` (`minItems: 1`) — the step_ids being folded into the summary, which is what the post-compaction provenance lineage references. Claude Code's `PreCompact` event carries no entry list, so an honest payload cannot be built; an empty or fabricated list would defeat the hook's provenance-laundering defense. This is a documented Guardian visibility gap (the adapter's `KNOWN_UNMAPPED` set), not an oversight.

**Deliberately not mapped — the skill lifecycle set (`steps/skillRegister`, `steps/skillLoad`, `steps/skillUnload`).** Claude Code fires no hook event when a skill registers, activates, or unloads, and the payloads' integrity fields (`definition.digest`, the registration-bound load path) appear in no hook event, so an honest payload cannot be built. A skill *invocation* is governed: it arrives as `PreToolUse` for the `Skill` tool and routes through `steps/toolCallRequest` like any other tool call. Lifecycle wiring becomes possible when the platform exposes skill lifecycle events.

Any other Claude Code hook event reaching the adapter (upstream renames, events wired in `settings.json` that the adapter doesn't know) emits an `unmapped_hook_event` audit line and lets Claude Code proceed — an ungoverned event is recorded as ungoverned, never silently dropped. Unmapped today: `PermissionRequest` and other lifecycle events with no semantic ACS equivalent in v0.1.0.

## Disposition mapping

Block-shape hooks are `UserPromptSubmit`, where a block stops the prompt, and `PostToolUse`, where a block only adds the reason next to the tool's output, so the adapter also replaces that output where Claude Code applies a replacement (see the mapping table). A fail-closed decision failure on `PostToolUse` withholds the output the same way. `Stop` is **audit-only** — Claude Code reads `{"decision":"block"}` on it as "do NOT stop, keep going," so the adapter never emits a block there; a Guardian `deny` is recorded (`unenforceable_decision`) and nothing is emitted. (`SubagentStop` is not forwarded at all — see the mapping table.)

| ACS disposition | Claude Code response on `PreToolUse` | Response on `PostToolUse` / `UserPromptSubmit` |
|---|---|---|
| `allow` | empty: Claude Code's own permission rules and prompt still decide (a `permissionDecision` of `"allow"` would skip the prompt) | empty (Claude Code proceeds) |
| `deny` | `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "…"}}` | `UserPromptSubmit`: `{"decision": "block", "reason": "..."}`. `PostToolUse`: the block plus `updatedToolOutput` holding a withheld notice (see the mapping table) |
| `modify` | `…"permissionDecision": "ask", "updatedInput": {…}`: the user sees and approves the rewritten call. The `parameter_overrides` are MERGED onto the original input (Claude Code replaces the whole input, so sending overrides alone would drop other arguments); substituted to `deny` if there is no usable object | `PostToolUse`: `updatedToolOutput` holding `modified_content` for `Bash` and MCP tools; withheld like a `deny` when there is none or the tool is another built-in, where the adapter cannot tell which field the content replaces |
| `ask` | `…"permissionDecision": "ask"` — **native**; Claude Code surfaces its own approval prompt. Auto mode runs `SubagentHandback` with no prompt, so there an ASK is a `deny`, audited as `unenforceable_decision`, and a MODIFY is `"allow"` with `updatedInput`, so the rewritten report is what is delivered | `PostToolUse`: withheld like a `deny`, since the tool already ran; `UserPromptSubmit`: substituted to `block` |
| `defer` | substituted to `deny` + `defer_substituted_deny` audit event (no native defer in `permissionDecision`) | `PostToolUse`: withheld like a `deny`; `UserPromptSubmit`: substituted to `block` |

An arrived decision the host CANNOT apply is substituted to a block/deny (never silently proceeded) and audited. A MODIFY the host cannot apply is a DENY recorded as `modify_unsupported` with `reason_codes: ["modify_unsupported"]` (§6.5): redactions or replacement content on a tool call, structured edits on a tool result, replacement content for a built-in tool other than `Bash`, whose output shape the hooks reference does not document, and any MODIFY on a prompt. Note the ASK and DEFER substitutions here are **deployment behavior, not spec-mandated**: §9.2 places disposition substitution on the Guardian, and §6's `timeout_decision: deny` default governs an *expired* defer, not an instant client-side substitution. A deployment that needs approver-driven resumption should run ACS-Core's ASK/DEFER flow at the Guardian layer and have the Guardian return an effective decision before responding to the adapter. A contradictory `modifications` object (both wholesale + structured, or overlapping targets) fails closed to `deny` per §6.3.

## Concurrency

Claude Code can run the hooks of parallel tool calls at the same time. The first hook process of a session holds the session's startup lock while it sends the session's one `handshake/hello` and its `steps/sessionStart`; it records how `sessionStart` went in a signed startup record next to the session record. Every other hook process of the session waits for that lock and follows the recorded outcome, so the Guardian sees the handshake, then `sessionStart`, then the session's other steps. A hook process that cannot take the lock, or finds a startup record that fails its checks, refuses the session and audits why. A start claimed by a hook process that ended before recording its outcome, as when the host cancels a hook at its timeout, is recorded once as a `sessionStart` without a decision (`session_start_incomplete`, failure class `observed_agent_error`), so each later hook settles its step with its own fail posture and `sessionEnd` reports it. `UserPromptSubmit` and `Stop` open and close the turn, and a signed session's first MCP tool call records `profile_claim_degraded`; other tool hooks only read session state. Every write of session state is one locked read-modify-write through a temp file of its own, and apart from the startup lock, no lock is held during a Guardian round trip. The Guardian's rolling `chain_hash` orders steps by arrival, so the order of concurrent steps is the order they reach the Guardian. A second wired copy of the adapter would send every event twice, and both requests for one tool call would carry the same `request_id`, so `acs-claude-code-wire` refuses to wire when it finds one in user, project, local or managed settings, in the hooks of an installed plugin that `enabledPlugins` turns on, or, for a settings file Cursor imports, in a `hooks.json` Cursor loads.

## Conformance posture

The Claude Code adapter covers ACS-Core's mandatory floor as listed below. This is the floor the tests check, not a full ACS-Core conformance claim (see `adapters/README.md`). Every row below describes what the code in `adapter.py` actually does — this table drifted from the code once (PR #22 review caught six false claims in it), so treat the code as ground truth and this table as its description:

- Handshake: `handshake/hello` is performed on the first hook event of a session, and its answer decides the session (§4.1): a verified ServerHello negotiates; a refusal, or an answer that fails its checks, refuses every step; and no answer leaves the session with no negotiated Guardian, so each hook's `ACS_STARTUP_POSTURE` applies (`proceed` lets the step run with nothing sent to the Guardian; `refuse` denies it). The decision is stored in `~/.cache/acs-adapter-handshake/` with an HMAC under the session key over the decision, the session and the Guardian URL, and holds for the session's lifetime, so a dead Guardian costs one timeout per session; a record that fails its checks, or a decision that cannot be stored, refuses the session. The ServerHello's response envelope is signature-verified and bound to the ClientHello before it is stored; its `on_decision_failure` combines with `ACS_DEFAULT_DENY` (deny wins over proceed), and its `timeout_config` replaces the local decision timeout, per method where `per_method_ms` names one (§6.4). The ServerHello must answer the ClientHello: a `negotiated_version` sharing a major version the adapter offered, a `methods_evaluated` list, the one transport the adapter offers (its Guardian URL's scheme), a positive `timeout_config.default_ms`, an `on_decision_failure` of `proceed` or `deny`, and only profiles the adapter claimed; otherwise the session has no negotiated Guardian (`invalid_server_hello`). Its `methods_evaluated` bounds what is sent: a method the Guardian omits resolves as ALLOW-by-default without being sent (handshake.json) and is recorded as `method_not_evaluated`; the hook returns no output, so Claude Code's own permission flow still applies, and a result never cites a request that was not sent. With no negotiated list, every mapped hook is sent. `ACS_HANDSHAKE=0` skips the handshake, and the startup posture settles every step.
- Turns: a `UserPromptSubmit` opens a turn with an explicit `steps/turnStart` (decision-eligible) before the `steps/userMessage`; `Stop` closes it with `steps/turnEnd`, `StopFailure` with outcome `error`, and the next `UserPromptSubmit` with outcome `interrupted` when neither ran. The `turn_id` is held in per-session state and stamped on `metadata.turn_id` of every in-turn step; session-level steps (`sessionStart`/`sessionEnd`) carry none.
- Dispositions: on `PreToolUse`, ALLOW prints nothing, so Claude Code's own permission rules and prompt still decide; DENY and ASK are honored natively (`permissionDecision`); MODIFY is an `ask` carrying `updatedInput` (overrides merged onto the original input) when a usable `parameter_overrides` object is present, so the user approves the rewritten call; DEFER substitutes to deny with an audit event. On `PostToolUse` the tool has already run: a DENY, ASK, DEFER or unusable MODIFY replaces the output Claude sees (see the mapping table) and is recorded as `unenforceable_decision` when the hook carries no output to shape a replacement on. **Lifecycle hooks (`Stop → agentResponse, turnEnd`, `StopFailure`, `SessionEnd`) are observation-only**: Claude Code fires them after the reply / turn / session has completed, so a Guardian `deny` is recorded as `unenforceable_decision`, and a MODIFY as `modify_unsupported`, and neither can undo it. Deployments needing pre-delivery gating place the gate at `UserPromptSubmit` (prompt / turn start) for prompts and `PreToolUse` for tools.
- Session context: `session_id` comes from Claude Code's own hook event field on every request; the Guardian-side audit chain accumulates against it. `agent_id` is `ACS_AGENT_ID` when set, else derived as `claude-code:<sha8(dir)>` from `CLAUDE_PROJECT_DIR`, or from the `cwd` of the session's first hook, since Claude Code's `cwd` follows Claude's `cd`. Turn state and decision-failure counts are keyed on the session alone.
- Replay protection: `request_id` (UUID) and `timestamp` are populated on every request. `PreToolUse` request_ids are deterministic (UUID5 of Claude Code's `tool_use_id`) so the matching `PostToolUse` can cite `request_id_ref`.
- Baseline integrity: HMAC-SHA256 per §10 over the RFC 8785 (JCS) canonical envelope, with an HKDF-derived per-session key from `ACS_HMAC_SECRET_FILE` / `ACS_HMAC_SECRET`. The signature names the configured label `ACS_HMAC_KEY_ID` as `key_id`, and a response under any other label fails verification with no other secret tried; an unsigned `SIGNATURE_INVALID`, a Guardian's answer to a label it does not hold, is recorded as `key_id_rejected` and fails closed. `rfc8785` is a hard dependency (no fallback canonicalization — §10 permits none). Responses are signature-verified AND bound to their request (`id` + `request_id`) under any HTTP status; a mis-bound, badly-signed or unverifiable response fails closed regardless of posture. A hook with no secret, a secret under 32 bytes, or no label refuses its session and sends nothing (`secret_missing`, `secret_too_short`, `key_id_missing`), whatever the posture: ACS-Core signs every request.
- Decision honoring: the fail posture defaults to `proceed` (fail-open with audit event), matching §6.4's default. `ACS_DEFAULT_DENY=1` or a ServerHello `on_decision_failure: deny` flips it to fail-closed (most-restrictive-wins). Guardian **refusals** (`SIGNATURE_INVALID`, `REPLAY_DETECTED`, `TIMESTAMP_OUT_OF_WINDOW`, malformed/oversized envelope) always fail closed regardless of posture — a refusal is an alive Guardian rejecting the envelope, and each refusal is attacker-reachable (spec issue #32). Before signing, every step replaces what RFC 8785 cannot encode: a lone surrogate becomes U+FFFD, and an integer past 2^53 - 1, NaN or an infinity becomes a string, recorded as `envelope_normalized`, so the Guardian still sees the step. An envelope that still cannot be signed is denied whatever the posture (`envelope_not_signable`) on `PreToolUse`, `UserPromptSubmit` and `PostToolUse`, whose output is withheld; on other hooks it follows the posture. A decision result without what response-envelope.json requires (`type: "final"`, `acs_version`, `request_id`, exactly one of the five decisions, and the `reasoning`, `modifications`, `ask_details` or `defer_details` its decision requires) is a `malformed_response` decision failure: an `allow` follows the posture, and any other verdict is denied whatever the posture, since carried out as an allow an unreadable or restrictive verdict could run what the Guardian denied (spec issue #32). Every decision failure is audited under either posture with its `failure_class` (`timeout`, `unreachable`, `malformed_response`, `guardian_error`, `observed_agent_error`, `signature_invalid`, `handshake_failure`, `other`) and `posture`, and `sessionEnd` reports the session's count per class in `summary.decision_failures` (§6.4, #273). A handshake that gets no answer is audited as `handshake_failure`; that session sends the Guardian nothing, `sessionEnd` included (§4.1).
- Audit: every fail-open proceed, refusal, substitution, unevaluated method, and unmapped event emits an `ACS_AUDIT` line to stderr and, when `ACS_AUDIT_FILE` is set, appends to that file (0600).

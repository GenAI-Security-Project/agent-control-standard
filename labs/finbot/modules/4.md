# Module 4: Ask a human

## What you'll see

[FinBot](glossary.md#finbot) pays a vendor's invoice for 7500. With [ACS](glossary.md#acs) off, the payment goes straight through. With ACS on, a [policy](glossary.md#policy) rule sends any transfer above 5000 to a person first.

The amounts are plain numbers. The rule compares the number and ignores any currency.

You approve one payment on the approver page and reject another. The approver page is a small web page where a person answers held payments. The approved one goes through. The rejected one never moves any money.

## Before you start

Run every command from `labs/finbot`. The lab must already be set up and running. If you skipped module 1, run the three commands at the top of its Before you start first: `doctor`, then `init`, then `up`.

These commands put the lab in a known state, so this module runs on its own. The module 3 solution stays live, and the module 4 rule starts as the starter.

```sh
./lab.sh mode off
./lab.sh sign mldsa
./lab.sh policy 3 solution
./lab.sh policy 4 starter
./lab.sh policy 5 starter
./lab.sh policy 6 starter
```

Open the viewer now. It paints only rows that arrive after the page loads.

```sh
./lab.sh viewer
```

## Run it with ACS off

The s4a scenario registers a vendor and sends in invoice INV-1042 for 7500. FinBot's payments [agent](glossary.md#agent) reads it and pays it.

```sh
./lab.sh run s4a
```

The payment goes through with nobody asked. The [gateway](glossary.md#gateway) is off, so no [Guardian](glossary.md#guardian) sees the [tool call](glossary.md#tool-call). The run record under `state/runs/` saves FinBot's list of transfers, which now holds the 7500 payment.

## Run it with ACS on

### Finish the rule

Open `policy/payment_threshold.rego` in any text editor. It has two `ask_requests` rules. Each rule's body ends in a line that reads `false`, so it never matches.

The comment above each rule names what goes in place of its `false`. Replace only that line. The rest of each rule stays as it is.

The first rule asks when the amount is readable and above the threshold. Its comment says to replace `false` with `amount_readable` and `not amount_within_threshold`. Finished, it reads:

```rego
ask_requests contains {"amount": amount, "question": sprintf("Approve a transfer of %v?", [amount])} if {
	tool_call
	tool_name == "finstripe__create_transfer"
	amount := arg("amount")
	amount_readable
	not amount_within_threshold
}
```

The second rule asks when the amount is missing or isn't a number. Without it, a transfer with no readable amount would go through. Its comment says to replace `false` with `not amount_readable`:

```rego
ask_requests contains {"amount": null, "question": "Approve a transfer whose amount the policy could not read?"} if {
	tool_call
	tool_name == "finstripe__create_transfer"
	not amount_readable
}
```

`finstripe__create_transfer` is FinBot's tool that moves money. `tool_call`, `tool_name` and `arg()` come from `policy/base.rego`, and `arg("amount")` reads the call's amount. `amount_readable` and `amount_within_threshold` sit at the bottom of your file.

`amount_readable` holds when the amount is a number. `amount_within_threshold` holds when it's at or under the threshold.

Keep the `tool_call` line in both rules, because a transfer's [tool result](glossary.md#tool-result) carries no arguments. Without that line, the second rule would hold each result for a person. FinBot would then lose the result of a payment that already went through.

The threshold, 5000, lives in `policy/data.json` as `payment_ask_threshold`.

If your edit breaks the rule, or you want to start over, put the starter back:

```sh
./lab.sh policy 4 starter
```

### Approve one payment and reject one

Switch to [enforce mode](glossary.md#enforce-mode), then open the approver page.

```sh
./lab.sh mode enforce
./lab.sh approver
```

The approver page runs only in enforce mode. The approver command prints its address, and the page asks for a token. Anyone holding the token can release a held payment.

The token is one line in the file `state/secrets/approver.token`. Open that file in a text editor, copy the line, and paste it into the page.

The mode change restarts the gateway, which signs you out of the approver page. If you opened the page earlier, reload it and enter the token again.

Now run s4a twice, once for each answer.

```sh
./lab.sh run s4a --answer approve
./lab.sh run s4a --answer reject
```

The `--answer` flag clicks for you. It answers through the approver page with the token, as you would. So you don't click anything in these two runs.

Watch the viewer during each run. A row reads "Ask: the call waits for a human approver" when the gateway holds the transfer. A second row reads "Ask resolved", with the outcome approved or rejected.

The flag answers within a second. The approver page may show the held transfer for a moment, or it may clear before it repaints.

To click yourself on a later try, run s4a without the `--answer` flag. The run waits in your terminal while you click in the browser. The page shows the held transfer, its arguments and the question "Approve a transfer of 7500?".

An ask nobody answers waits at most 240 seconds. Then the gateway denies the call. A timeout counts as a reject, never as an approval.

### Pay a small invoice

The s4b scenario sends in invoice INV-1043 for 950, under the threshold.

```sh
./lab.sh run s4b
```

No ask row shows up in the viewer, and nothing waits on the approver page. The transfer goes straight through.

## What changed

With ACS off, the 7500 payment went through with nobody asked.

With ACS on, the Guardian's [decision](glossary.md#decision) on the transfer was ask. Ask is a fourth kind of decision, after allow, deny and modify. The gateway held the call and listed it on the approver page.

When the run approved, the gateway sent the same call back to the Guardian with the answer. The Guardian's next decision allowed it, and the payment went through.

The approval doesn't release the call by itself. Only the Guardian's next decision does.

When the run rejected, the gateway denied the call and sent nothing back to the Guardian. No money moved.

The 950 payment sat under the threshold, so the rule never asked.

## What ACS gave you

- A rule you can read decides which payments wait for a person.
- The approver page is the one place to answer, and it needs its own token.
- A record of each answer. The [audit log](glossary.md#audit-log) holds one `ask_resolved` line for each call the gateway held, with its outcome: approved, rejected or timed out.
- A call FinBot can't bypass. FinBot never talks to the Guardian, and the gateway holds the call until the Guardian decides. <!-- claim:C-17 -->

## What this doesn't show

- The answer field the approver page sends is a lab convention until issue #175 settles it. <!-- claim:C-13 -->
- Nobody signs the approver's answer yet. The audit log records it on the gateway's word alone.
- The rule judges the amount the model put in the call. It doesn't check the amount against the invoice.
- One person, one page, one token. The lab has no approver roles and no second approver.

## Check your work

```sh
./lab.sh check 4
```

The check reads the run records and the audit log. It looks for one finished s4a run with an approved ask and the 7500 transfer. It also looks for one with a rejected or timed out ask and no transfer. Both must run under the same policy.

A pass prints one line like this, with your own run ids:

```text
DONE: run 20261209T101500Z-s4a was approved and moved the 7500 transfer, and run 20261209T102000Z-s4a was refused and moved nothing, both under one policy
```

A NOT YET line says which half is missing and names the command to run next. After only the approved run, it starts like this:

```text
NOT YET: You have an approved run (20261209T101500Z-s4a) and still need one where the ask is refused.
```

Checks read `state/`, so anything that can write `state/` can steer a check. A check believes the files it finds there, so a file planted there could fool it. That is this lab's [trust boundary](glossary.md#trust-boundary), and module 7 comes back to it.

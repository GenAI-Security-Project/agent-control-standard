# Module 1: Wire it in

## What you'll see

### What ACS is

[ACS](glossary.md#acs) says how an AI [agent](glossary.md#agent) checks with a separate service before it acts. The name stands for the OWASP Agent Control Standard. The service is the [Guardian](glossary.md#guardian). It answers each question with a [decision](glossary.md#decision): allow, deny, modify or ask.

The agent in this lab is [FinBot](glossary.md#finbot), a finance assistant built to be attacked. FinBot doesn't speak ACS itself. The lab puts a [gateway](glossary.md#gateway) between FinBot and its model. The gateway sends each [tool call](glossary.md#tool-call) to the Guardian and applies the answer.

The gateway has three modes. In off mode it asks the Guardian nothing. In [shadow mode](glossary.md#shadow-mode) it asks and records, but applies nothing. In [enforce mode](glossary.md#enforce-mode) it applies every decision.

### What you need

- Docker. On macOS that's Docker Desktop. On Linux it's Docker Engine with the Compose v2 plugin. Windows is untested. <!-- claim:C-16 -->
- At least 6 GiB of memory for Docker. Set it in Docker Desktop's resources on macOS.
- The lab bundle, which is the `labs/finbot` folder of the ACS repository.
- A terminal open in `labs/finbot`, and a web browser.

You don't need a model key. The model's answers come from recordings, as this module shows.

### What happens in this module

FinBot onboards a new vendor, Northwind Supplies. You run that twice, once with ACS off and once in enforce mode. Then you compare what each run left behind.

With ACS off, FinBot's tool calls run with no decision and no record. With ACS on, each tool call waits for the Guardian's answer.

The decision viewer, a page in your browser, shows two moments of this module. The handshake is the gateway and the Guardian agreeing how to talk. The first allow is the first tool call the Guardian lets through.

## Before you start

Work from `labs/finbot`. Check your machine, set the lab up, and start it.

```sh
./lab.sh doctor
./lab.sh init
./lab.sh up
```

The `doctor` step prints one line per thing it checks. A healthy machine prints DONE lines like these, with its own numbers:

```text
DONE: Docker is installed and running
DONE: Docker Compose v2.29.1
DONE: Docker has 8 GiB of memory
DONE: architecture arm64
DONE: port 8095 is free
```

A NOT YET line says what to fix. Fix it, then run `doctor` again before you go on.

The `init` step creates the lab's secrets and the Guardian's signing keys. It prints the Guardian's [fingerprint](glossary.md#fingerprint), a short hash of its public key, and writes it to `.env`. Yours is `sha256:` and 64 hex digits:

```text
DONE: lab initialized. Guardian decision key lab-guardian-1, fingerprint sha256:4f0a9c...
```

If `init` prints "NOT YET: lab is already initialized", that's fine. Keep the lab you have and go on. Don't use `--force`, because it replaces every key.

The `up` step starts the lab's containers. The first time, it downloads or builds the images, so it takes longer than later starts. It returns once every service is running.

Now set the lab the way this module expects. The Guardian signs its decisions with [ML-DSA-65](glossary.md#ml-dsa-65), a scheme in which only the Guardian holds the signing key. <!-- claim:C-02 -->

Modules 3 to 6 each have a [policy](glossary.md#policy) for you to finish. The starter is the unfinished version, and the solution is the finished one. These commands put every starter back and turn ACS off.

```sh
./lab.sh sign mldsa
./lab.sh policy 3 starter
./lab.sh policy 4 starter
./lab.sh policy 5 starter
./lab.sh policy 6 starter
./lab.sh mode off
```

Open the decision viewer before you run anything. It paints only rows that arrive while the page is open. Rows already on disk when the page loads never appear.

```sh
./lab.sh viewer
```

The command prints the page's address and returns. Open that address in your browser, and leave the tab open.

## Run it with ACS off

```sh
./lab.sh run s1
```

A scenario is a scripted visit to FinBot, and s1 is the first one. It starts FinBot from empty data and registers Northwind Supplies. Then it waits for FinBot's onboarding agent to go quiet.

Quiet means FinBot has stopped calling its model. The lab waits at most seven minutes. Then the run prints a line like this, with its own run id:

```text
DONE: s1 ran in off mode and FinBot went quiet. Run record state/runs/20261209T100000Z-s1.json
```

Look at the viewer. Above its empty table it reads "no ACS record". FinBot's model calls went through the gateway and landed in the [model input log](glossary.md#model-input-log).

No [transcript](glossary.md#transcript) changed, and the [audit log](glossary.md#audit-log) shows no session. Off mode leaves no ACS record at all.

See what FinBot sent its model. This prints the newest line of the model input log as JSON.

```sh
./lab.sh model-log
```

Look for two parts. The `tools` list holds the tools FinBot offered its model. The `input` list holds the conversation the model read.

The model's answers come from [replay](glossary.md#replay), so the lab needs no model key and no connection to a model provider. <!-- claim:C-08 -->

## Run it with ACS on

Jaeger is an optional trace viewer, and a span is its record of one request. No check reads it. The gateway sends spans only for traffic after you turn traces on.

If you want to see this run in Jaeger too, turn traces on now.

```sh
./lab.sh traces on
```

Now run s1 with ACS on.

```sh
./lab.sh mode enforce
./lab.sh run s1
```

In enforce mode the gateway applies every decision. Watch the viewer while the run goes.

The handshake comes first. The gateway's opening message, the ClientHello, offers ML-DSA-65 for decisions. The Guardian's reply, the ServerHello, names it.

Each message the gateway sends the Guardian names a step. The first is `steps/sessionStart`, which opens the session.

The first allow comes next. FinBot's agent asks to run a tool, and the gateway sends that to the Guardian as `steps/toolCallRequest`. <!-- claim:C-06 --> The Guardian allows it, and only then does FinBot run the tool.

When the tool returns, its [tool result](glossary.md#tool-result) goes to the Guardian as `steps/toolCallResult`. <!-- claim:C-06 --> The model reads it only after the Guardian answers.

Now look at the [signature](glossary.md#signature) column, the sixth column of the table. Each Guardian answer reads ML-DSA-65 there, and the Check column beside it reads verified. <!-- claim:C-02 --> <!-- claim:C-04 -->

The viewer checked each answer's signature against the Guardian's [key document](glossary.md#key-document) as it arrived. <!-- claim:C-04 --> A verified mark covers one answer, not the whole transcript. <!-- claim:N-04 -->

The check at the end reads the whole session. That includes the audit chain, a hash chain that links each request to the one before it. <!-- claim:C-03 -->

With the starters live, every call in this run reads allow but one. FinBot ends onboarding by emailing the vendor, and module 3's starter rule denies that email because the vendor's address is outside the company. You fix that rule in module 3.

## What changed

Between your two runs, only the gateway's mode moved. The off run left every transcript as it was. The on run opened a session and wrote each request and answer to its transcript.

The lab runs FinBot's own code at commit 1450fc4, unchanged, and changes four of its settings in `compose.yaml`. <!-- claim:C-01 -->

`OPENAI_BASE_URL` and `OPENAI_API_KEY` point FinBot's model traffic at the gateway, with the lab's client token as the key. <!-- claim:C-01 --> `LLM_TIMEOUT` gives the model more time, and `WEB_CONCURRENCY` runs one web worker. <!-- claim:C-01 -->

The Guardian decides only the steps the gateway sends it. ACS defines nineteen [hooks](glossary.md#hook), the points where an agent asks first. <!-- claim:C-06 -->

The gateway sends four of them: `steps/sessionStart`, `steps/toolCallRequest`, `steps/toolCallResult` and `steps/sessionEnd`. <!-- claim:N-06 --> Only the tool call and the tool result carry a decision the gateway applies. <!-- claim:C-06 -->

## What ACS gave you

You got a record you can check after the fact. Each Guardian decision in the on run carries an ML-DSA-65 signature. <!-- claim:C-02 --> In this lab only the Guardian holds the private key that makes one. <!-- claim:C-02 -->

Requests from the gateway work differently. They carry an [HMAC](glossary.md#hmac) signature, made with a key the gateway and the Guardian share. <!-- claim:C-02 -->

FinBot can't bypass the Guardian, and the reason is how the lab is wired. <!-- claim:C-17 --> FinBot reaches its model only through the gateway, which wants the lab's client token. The Guardian sits on a network FinBot can't reach. <!-- claim:C-17 -->

Some of what you saw isn't in the v0.1.0 specification yet. <!-- claim:C-13 --> The ServerHello field `x_acs_lab_response_algorithm` is a lab convention until issue #316 settles it. <!-- claim:C-13 --> The key document format is a lab convention until issue #460. <!-- claim:C-13 -->

If you turned traces on, Jaeger's page is at http://127.0.0.1:16686/, or at the port you set as LAB_PORT_JAEGER in `.env`. It shows the enforce run as spans. Turn traces off again when you're done.

```sh
./lab.sh traces off
```

## What this doesn't show

ACS names seven of its nineteen hooks as the minimum an agent sends. The lab sends four of those seven, so it doesn't claim to be ACS-Core conformant. <!-- claim:N-06 -->

FinBot's tools run on MCP servers, and MCP is the Model Context Protocol. ACS has no wire format yet for an MCP call wrapped this way (issue #383). <!-- claim:N-06 -->

A signature covers one decision. It doesn't show that the gateway carried out a decision, or that every step reached the Guardian. <!-- claim:N-04 -->

Replay isn't a live model. A request the recordings don't cover gets a fixed neutral reply, and the viewer marks it. <!-- claim:C-08 -->

This module writes no policy. The one deny you saw comes from module 3's starter rule, and you rewrite that rule in module 3.

## Check your work

```sh
./lab.sh check 1
```

DONE means the off run left no ACS record and the on run holds one full session. <!-- claim:C-03 --> The check ran acs-verify, the ACS tool that checks a transcript's signatures and audit chain, on that session. <!-- claim:C-03 --> It used the key document and the fingerprint from `.env`. <!-- claim:C-03 -->

A pass prints one line like this, with your own run id, session id and fingerprint:

```text
DONE: module 1. With ACS off, FinBot reached the model through the gateway and left no ACS record. Enforce run 20261209T101000Z-s1 governed every call, and acs-verify passed session <session id> under ML-DSA-65 with the Guardian's key sha256:4f0a9c...
```

A NOT YET line names the next command to run. Run it, then run the check again.

Checks read `state/`, so anything that can write `state/` can steer a check. A check believes the files it finds there, so a file planted there could fool it. That is this lab's [trust boundary](glossary.md#trust-boundary), and module 7 comes back to it.

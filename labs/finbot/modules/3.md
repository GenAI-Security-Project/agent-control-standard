# Module 3: Stop it

## What you'll see

In module 2, [FinBot](glossary.md#finbot) mailed vendor data to an outside address, and the mail landed in the [dead drop](glossary.md#dead-drop). Here you write a [policy](glossary.md#policy) rule that denies that send.

The first rule you try also denies a vendor's own payment notice. You fix it so the notice goes through and the leak still doesn't. You finish when one policy does both.

## Before you start

Work from `labs/finbot`. If you skipped module 1, run the three commands at the top of its Before you start first: `doctor`, then `init`, then `up`.

These commands start the lab and put the [gateway](glossary.md#gateway) in [enforce mode](glossary.md#enforce-mode). They have the [Guardian](glossary.md#guardian) sign each [decision](glossary.md#decision) with [ML-DSA-65](glossary.md#ml-dsa-65), and put the starter of every module's policy live.

```sh
./lab.sh up
./lab.sh mode enforce
./lab.sh sign mldsa
./lab.sh policy 3 starter
./lab.sh policy 4 starter
./lab.sh policy 5 starter
./lab.sh policy 6 starter
```

In `policy 3 starter`, the 3 is the module number. The starter is the unfinished policy you start from, and the solution is the finished one.

Every run here uses [replay](glossary.md#replay), so the model's answers come from recordings. <!-- claim:C-08 -->

Open the decision viewer now, before the first run, and keep it open beside this guide. It shows a row for each decision the Guardian makes.

```sh

```

## Run it with ACS off

This module has no off run of its own. Module 2's off run is the picture before any rule: the send goes out, and the dead drop gets the mail. Go back to module 2 if you want to see it again.

## Run it with ACS on

### The starter rule

The live rule is in `policy/outbound_email.rego`, written in [Rego](glossary.md#rego), the policy language. [OPA](glossary.md#opa), the policy engine, runs it for the Guardian.

The starter allows mail only to company mailboxes. FinBot gives each player session its own namespace, and company mailboxes end in `@<namespace>.finbot`. Any other recipient gets a deny with the reason code `external_recipient`, a short label for why.

This is the starter's line that decides which recipients pass:

```rego
recipient_allowed(address) if internal_address(address)
```

Run the attack in s2 first.

```sh
./lab.sh run s2
```

Watch the viewer. A row for `finmail__send_email` appears with a deny and the reason `external_recipient`. The Guardian denied the [tool call](glossary.md#tool-call), so the mail never left.

The run prints FinBot's reply before its result. In s2 that reply is the [neutral deny line](glossary.md#neutral-deny-line): "I couldn't complete that action."

Now run the vendor's notice in s3.

```sh
./lab.sh run s3
```

In s3 the vendor asks for a payment notice at its own address, `ap@northwind-supplies.example`. Watch the viewer again. Another `finmail__send_email` row appears with a deny and `external_recipient`. That address isn't a `.finbot` mailbox, so the starter denies it too.

Run the check.

```sh
./lab.sh check 3
```

The check says NOT YET, and it names s3. The line starts like this:

```text
NOT YET: the rule also blocked the vendor's own payment notice in s3. In s3's run, 0 messages reached an outside address and 0 messages reached the vendor's inbox. To fix it, add a rule for the vendor list to policy/outbound_email.rego and the vendor's domain to vendor_domains in policy/data.json,
```

The line ends with the command that writes the answer for you, and the two runs to repeat. The check counts the mail each run added to two mailboxes. The dead drop holds mail that went outside, and the vendor's inbox holds mail the vendor got.

That's the starter's trap. A rule that denies all outside mail also denies the mail the business needs.

### Fix the rule

Teach the rule about the vendors the company pays. Open `policy/outbound_email.rego` in any text editor. Find the `recipient_allowed` line shown above, and add this rule on the lines right after it.

```rego
recipient_allowed(address) if {
	match := regex.find_all_string_submatch_n(`^[^@\s]+@([^@\s]+)$`, address, 1)
	domain := lower(match[0][1])
	some vendor in data.finbot_lab.vendor_domains
	lower(vendor) == domain
}
```

The new rule takes the part of the address after the `@` and allows it when that domain is on the vendor list. Rego doesn't care about indentation, so tabs or spaces both work.

Then open `policy/data.json`. It holds this line, an empty vendor list:

```json
"vendor_domains": []
```

Change that line to this one, and leave the rest of the file as it is.

```json
"vendor_domains": ["northwind-supplies.example"]
```

OPA reloads both files on its own, with no restart. If a file doesn't compile, OPA writes the error to its log, and every governed step is denied until you fix it. This shows the log:

```sh
./lab.sh logs opa
```

The starter's two deny rules each open with a `tool_call` line. `tool_call` comes from `policy/base.rego`, and it holds only for a tool call, never for a [tool result](glossary.md#tool-result).

Your new rule isn't a deny rule, so it needs no `tool_call` line. If you write a deny rule of your own, open it with `tool_call` too. A tool result carries no arguments, so a rule that reads recipients would otherwise deny the result of a send it allowed.

## What changed

The attack in s2 still gets a deny with `external_recipient`, and no new mail reaches the dead drop. The notice in s3 now gets an allow, and it lands in the vendor's inbox.

The only thing you edited was the policy. FinBot's code and the gateway stayed as they were.

When the Guardian denies a send, the model reads the neutral deny line in place of the tool's output: "I couldn't complete that action." That line is the one thing the [agent](glossary.md#agent) sees when a control acts. <!-- claim:C-17 -->

So the agent can tell it was blocked, as with any enforcement point. It still can't bypass the Guardian, because the send runs only after the Guardian allows it. <!-- claim:C-17 -->

## What ACS gave you

A control point FinBot can't bypass. Each send the model asks for goes through the gateway to the Guardian before FinBot runs it. <!-- claim:C-17 -->

A rule in plain Rego that you can read and edit, and one data file that holds the vendor list.

A record of each decision. The [audit log](glossary.md#audit-log) holds every allow and deny with its reason code, and the check reads it.

## What this doesn't show

Every `.finbot` mailbox counts as internal. The policy can't see which namespace belongs to this player, so a mailbox in another player's namespace passes too.

An email with no recipient is allowed. The rule judges recipients, and with none there is nothing for it to deny.

The vendor list allows a whole domain. Any address at `northwind-supplies.example` passes, not only the one the vendor registered. So this policy would let a leak to another address at that domain through, and that mail would land in the dead drop.

The rule reads the recipient fields only. It doesn't read the subject or the body, so it says nothing about what a mail carries.

The OPA input and verdict shapes are a lab convention until issue #531 settles them. <!-- claim:C-13 -->

Replay serves the answers that were recorded. It isn't a live model. <!-- claim:C-08 -->

## Check your work

```sh
./lab.sh check 3
```

When both runs passed under one policy, the line looks like this. Your run ids differ.

```text
DONE: one policy denied s2's outside send and let s3's vendor notice through. In s2's run, 0 messages reached an outside address. In s3's run, 0 messages reached an outside address and 1 message reached the vendor's inbox. Runs 20261209T103000Z-s2 and 20261209T104000Z-s3.
```

A NOT YET line counts the same mail and names the next command to run.

Each run first registers the vendor, and FinBot sends onboarding mail then. The check ignores that setup mail and counts only mail sent after it.

Checks read `state/`, so anything that can write `state/` can steer a check. A check believes the files it finds there, so a file planted there could fool it. That is this lab's [trust boundary](glossary.md#trust-boundary), and module 7 comes back to it.

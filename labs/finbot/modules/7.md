# Module 7: Forge a decision<!-- claim:C-04 -->

In modules 1 to 6 the [Guardian](glossary.md#guardian) made every [decision](glossary.md#decision). The [gateway](glossary.md#gateway) applied it, and [FinBot](glossary.md#finbot) had no way around it. <!-- claim:C-17 --> This module asks a harder question. Could the gateway, which carries every decision, write one the Guardian never made?

## What you'll see

You play the gateway turned forger. You take a deny the Guardian signed and rewrite it to allow, in a copy of the record. <!-- claim:C-04 -->

Under [HMAC](glossary.md#hmac) the [forgery](glossary.md#forgery) checks out, because the gateway holds the same key as the Guardian. Under [ML-DSA-65](glossary.md#ml-dsa-65) it fails at the forged line, because only the Guardian holds the private key. <!-- claim:C-04 --> <!-- claim:C-03 -->

Then you ask the Guardian to fall back to HMAC, and it refuses. <!-- claim:C-05 -->

## Before you start

Run every command from `labs/finbot`, with the lab already up. If you skipped module 1, run the three commands at the top of its Before you start first: `doctor`, then `init`, then `up`.

These commands put the lab in a known state. They set [enforce mode](glossary.md#enforce-mode), use the answer for every [policy](glossary.md#policy), and start on HMAC signing.

```sh
./lab.sh mode enforce
./lab.sh policy 3 solution
./lab.sh policy 4 solution
./lab.sh policy 5 solution
./lab.sh policy 6 solution
./lab.sh sign hmac
```

[ACS](glossary.md#acs) stays on in enforce mode for the whole module, and there is no off run. The steps end on ML-DSA-65 with a [downgrade](glossary.md#downgrade) probe, and the check needs both. So follow them in order.

The module 3 answer denies the email that leaks invoice data to an outside address. That deny is the decision you forge. <!-- claim:C-04 -->

## Make a forgery<!-- claim:C-04 -->

Run the attack scenario under HMAC. The Guardian denies the outside email, and the gateway writes the whole exchange to the session's [transcript](glossary.md#transcript).

```sh
./lab.sh run s2
./lab.sh forge
```

The forge command copies that transcript to `state/forged/`. In the copy, the deny on the outside email now says allow, and the forger signs it with the shared key. Every other line stays as the gateway wrote it. <!-- claim:C-04 -->

Then the forge command runs acs-verify on the copy for you. acs-verify is the ACS tool that checks a transcript's [signatures](glossary.md#signature) and its audit chain. <!-- claim:C-04 -->

Under HMAC it checks with the shared secret. The forge command prints a line like this one, with your line number: <!-- claim:C-04 -->

```text
DONE: the forged allow at line 12 verifies under HMAC. Anyone holding the shared key could have written it
```

DONE here means the forge step worked, so the forged allow passed. It passes because an HMAC signature is one both sides can make. <!-- claim:C-04 -->

Now switch decision signing to ML-DSA-65 and do the same thing again.

```sh
./lab.sh sign mldsa
./lab.sh run s2
./lab.sh forge
```

This time the copy fails, at exactly the line you forged: <!-- claim:C-04 -->

```text
DONE: the forged allow fails at line 12 under ML-DSA-65
```

The forger still holds the HMAC key, and it still signed the allow with that key. That signature isn't the Guardian's, so it fails. <!-- claim:C-04 -->

## Run it with ACS on

ACS has been on the whole time. This part checks the real session, then asks the Guardian to fall back.

The forged copy failed. Now confirm the real session passes, so you know the failure came from the forgery alone. <!-- claim:C-03 -->

```sh
./lab.sh verify --keys-only
```

The verify command checks every signature in the newest session against the Guardian's public key in the [key document](glossary.md#key-document). <!-- claim:C-03 --> The `--keys-only` flag checks the signatures and the key and skips the audit chain. The final check reads the chain. <!-- claim:C-03 -->

The command always gives acs-verify the [fingerprint](glossary.md#fingerprint) init printed. So a swapped key document fails too. It prints a line like this one, with your session id: <!-- claim:C-03 -->

```text
DONE: every signature in session <session id> verifies under ML-DSA-65 with the key lab init pinned
```

Next, play a client that can only check HMAC, and ask the Guardian for a session. This is the downgrade probe.

```sh
./lab.sh downgrade
```

The client's opening message, the ClientHello, offers HMAC only. The Guardian answers with the error `-32000 unsupported_signature_algorithm`, which means it won't sign with what the client offers. <!-- claim:C-05 -->

The Guardian signs that refusal with its ML-DSA-65 key. The downgrade command checks the signature against the pinned key, then prints: <!-- claim:C-05 --> <!-- claim:C-03 -->

```text
DONE: the Guardian refused a ClientHello offering only HMAC with -32000 unsupported_signature_algorithm, signed with the key lab init pinned. It signs decisions with ML-DSA-65 and won't fall back
```

"Won't fall back" covers the decision signature only. Requests stay on HMAC-SHA256, the HMAC variant the lab uses. <!-- claim:C-05 -->

The command also records the refusal, with the pinned fingerprint, in `state/verify/` for the check to read. <!-- claim:C-03 -->

Last, compare keys. Find the fingerprint init printed, in your terminal or in `labs/finbot/.env`. Open that file in a text editor, and look for the line `LAB_GUARDIAN_FINGERPRINT=`. Then print the Guardian's log.

```sh
./lab.sh logs acs-guardian
```

The log is long. Search it in your terminal for `[guardian] decision signing ML-DSA-65`. That line's `fingerprint=` value must match the one from init. When they match, the key you checked against is the key the Guardian signs with. <!-- claim:C-03 -->

## What changed

The scenario, the policy and the forger were the same both times. The only change was how the Guardian signs its decisions. <!-- claim:C-04 -->

HMAC uses one key that the gateway and the Guardian share. An HMAC check shows that nobody without the secret edited the log. <!-- claim:C-04 --> It can't say which side wrote an entry, as [section 8.6 of the specification](https://owaspacs.org/docs/spec/instrument/specification/#86-chain-head-publication-normative) says. <!-- claim:C-04 -->

ML-DSA-65 splits the key in two. The Guardian alone holds the private key that signs. Everyone else holds the public key, which can check a decision but can't make one. <!-- claim:C-03 -->

## What ACS gave you

A forged allow under ML-DSA-65 fails at its own line when someone checks it with the Guardian's public key. So you can check a decision without trusting the gateway that carried it. <!-- claim:C-04 --> <!-- claim:C-03 -->

That holds one decision at a time, and only when someone checks. <!-- claim:C-04 --> It also holds only when your copy of the public key came over a channel the forger doesn't control. <!-- claim:C-03 -->

That's why the fingerprint lives in `.env`. The gateway, the Guardian and the viewer can't read that file, because it isn't mounted into their containers. <!-- claim:C-03 -->

## What this doesn't show

The lab doesn't solve how a key gets published or revoked. The key document is a lab convention until issue #460 settles that. <!-- claim:N-03 --> <!-- claim:C-13 -->

A signature covers one decision. It can't show that the record holds every decision, or that the gateway obeyed a deny. A request that never reached the Guardian leaves no signed answer at all. <!-- claim:N-04 -->

Signing makes a forgery detectable by anyone holding the public key. It doesn't mean anyone looked. <!-- claim:C-04 -->

The refusal shows that this Guardian won't fall back. It covers the decision signature only. <!-- claim:N-05 --> <!-- claim:C-05 -->

Catching every downgrade needs the handshake bound to the traffic after it. Issue #13 would add that binding. <!-- claim:N-05 --> <!-- claim:C-05 -->

## Check your work

```sh
./lab.sh check 7
```

The check runs acs-verify again on both forged copies and on the real session. It doesn't take the forge results in `state/verify/` on trust. <!-- claim:C-04 -->

It passes when four things hold: <!-- claim:C-04 --> <!-- claim:C-03 --> <!-- claim:C-05 -->

- The forged copy from your newest HMAC run verifies under HMAC. <!-- claim:C-04 -->
- The forged copy from your newest ML-DSA-65 run fails at its forged line. <!-- claim:C-04 -->
- That real session verifies with the pinned fingerprint. <!-- claim:C-03 -->
- Signing is on ML-DSA-65 now, and `state/verify/` holds a downgrade refusal recorded under the fingerprint in `.env`. <!-- claim:C-05 --> <!-- claim:C-03 -->

After a new key or a switch back to HMAC, run the downgrade command again. A pass names both forged lines, the real session and the key. It starts like this: <!-- claim:C-04 -->

```text
DONE: module 7. The forged allow at line 12 of session <session id> verifies under HMAC-SHA256, so anyone holding the shared key could have written it. The forged allow at line 12 of session <session id> fails under ML-DSA-65, while the session itself verifies with the key sha256:4f0a9c...
```

Checks read `state/`, so anything that can write `state/` can steer a check. A check believes the files it finds there, so a file planted there could fool it. That is this lab's [trust boundary](glossary.md#trust-boundary).

This module shows why it matters. The gateway can write `state/`, and here the gateway plays the attacker. The check runs acs-verify itself on the forged copies and the session. <!-- claim:C-04 -->

The downgrade half is different. The check reads the result file the downgrade command wrote, and doesn't check the refusal's signature again. A forger who can write `state/` could plant that file. So run the downgrade command yourself and read its line. <!-- claim:C-05 -->
